---
title: Deployments
description: Review and deploy an environment's saved draft, inspect history, and restore configuration
---

A deployment is an immutable snapshot of an environment's configuration. It records the services, volumes, variables, resources, networking, message, and author at the time you deploy.

The canvas edits a **draft**. Editing that draft is separate from changing running infrastructure. A deployment applies the saved draft for the whole selected environment, not just the service whose panel is open.

## Review and Deploy

<Steps>
  <Step title="Prepare the draft">
    Select the project and environment you intend to change. Edit services on the canvas. Settings changes update the draft; runtime variable edits need **Save changes** in each service's **Variables** tab.
  </Step>

  <Step title="Review the changes">
    Click **Deploy** in the environment's changes banner. The dialog lists the additions, edits, and removals that will be deployed. Review the whole list, including changes made by teammates or agents.

    If **Can't deploy yet** appears, resolve the listed blockers first. These can include invalid configuration, unresolved variable references, or plan limits.
  </Step>

  <Step title="Check unsaved variables">
    If a service has unsaved variable edits, the dialog names it. Those edits are left out of this deployment. Close the dialog, open that service's **Variables** tab, and click **Save changes** if you want them included.
  </Step>

  <Step title="Add a message and confirm">
    Enter a **Message** describing the changes, or click **Generate** to create one from the diff. Confirm with **Deploy**.
  </Step>

  <Step title="Follow progress">
    Open **History** in the canvas. The deployment entry shows progress, outcome, and any recorded failure. For a service that fails to start, open its **Status** tab for runtime problems and platform events, and **Logs** for application output.
  </Step>
</Steps>

For example, if you raise a service's memory while a teammate has already changed another service's image, both saved edits appear in the review. Deploying the environment includes both.

## Undeployed Changes

The changes banner counts edits in the draft that differ from the deployed configuration. Canvas nodes also distinguish undeployed edits from runtime state: a service can be running while its draft has changes waiting to deploy.

Use **Discard changes** to return the draft to the deployed configuration. The confirmation lists what will be discarded. This does not stop the running environment, and discarded draft changes cannot be recovered with Undo.

## History

**History** combines deployment snapshots and image builds in one timeline. They are different events:

| Event | What to inspect |
| --- | --- |
| **Deployment** | Message, author, time, configuration changes, duration, and deployment outcome |
| **Build** | Repository, branch, commit, affected services, build outcome, and build logs |

Expand an entry for its details. Open a build's logs to inspect image-build output. Cancelled builds are shown separately from failures. A build failure and an application crash need different investigation: use build logs for the former and service Status/Logs for the latter.

For a deployment with a stored configuration snapshot, **View on canvas** opens that historical configuration. It is a preview until you choose **Restore as draft**.

Deployment history is retained on every plan. A historical configuration can be used as the starting point for a new deployment; volume contents are not part of the snapshot.

## Deployment State and Runtime State

Deployment progress and service runtime state describe different things. A deployment can be in progress while the previous version is still running. A completed deployment can later have a service crash. A failed rollout can leave services in different states.

The deployment history reports the operation's outcome. A service's **Status** tab reports runtime problems, metrics, and recent platform events. The environment header and canvas nodes provide status summaries. None of these is an application-level HTTP health check.

<Warning>
  Do not assume that a failed deployment made no changes or left every service untouched. Inspect History and the affected services before deciding whether to fix the draft or restore a previous configuration.
</Warning>

## Rollout Behavior

Stateless services use a rolling update strategy. A new instance starts alongside the old one; at most one extra replica runs during rollout, and replicas are not removed early. Once the new instance is running, traffic shifts to it and the old instance terminates.

<Warning>
  Suga does not run application health checks against your service. A process that has started can receive traffic before the application is ready to serve requests. Account for startup time and dependencies in your application.
</Warning>

### Services with Volumes

A service with a mounted volume has one replica and uses a recreate strategy:

1. The old instance stops and its volume detaches.
2. The volume attaches to the new instance.
3. The new instance starts.

This causes a gap in service during the handover. Volume rows can show **Provisioning** or **Attaching** while the platform prepares storage. Keep stateful services separate from stateless application services so their restarts do not require restarting the rest of the stack.

## Automatic Image Updates

Suga can roll out a new image without a manual deployment:

- **Images built by Suga:** with **Build on every push** enabled, a push to the watched branch triggers a build. A successful build rolls out the new image.
- **Pre-built registry images:** Suga periodically checks for a new image at the same tag and rolls it out when the digest changes.

Build events appear in History. An automatic image rollout does **not** create a new deployment snapshot. It reuses the active deployment's configuration and swaps the image, so it is not a new configuration version you can restore from deployment history.

To change runtime variables, resources, networking, or other infrastructure configuration, save the draft and deploy it from the canvas. Saving **Edit build settings** starts a build immediately; it does not wait for the draft's Deploy action.

## Restore a Previous Configuration

<Steps>
  <Step title="Open History">
    Open **History** in the environment's canvas and find the deployment you want to inspect.
  </Step>

  <Step title="View on canvas">
    Expand the deployment and choose **View on canvas**. Inspect its services and settings in the historical view. Choose **Close** to leave without changing the draft.
  </Step>

  <Step title="Restore as draft">
    Click **Restore as draft**. If the current draft has undeployed changes, Suga lists them and asks you to confirm **Replace changes**. Restoring replaces those draft changes; it does not deploy immediately.
  </Step>

  <Step title="Review and deploy">
    Review the restored draft, then click **Deploy**, add a message, and confirm. This creates a new deployment with the restored configuration and a new history entry.
  </Step>
</Steps>

### What Restoring Includes

The snapshot includes service images and function code, saved variables, resource allocations, replica counts, networking, and volume definitions.

It does **not** restore volume data, database records, or external service state. Restoring a configuration that removes a volume can delete that volume; check the diff carefully and back up data first. Database migrations may need a separate recovery procedure.

## Common Questions

<AccordionGroup>
  <Accordion title="Does saving a setting deploy it?">
    Runtime settings and saved service variables update the environment's draft. Review and deploy the draft to apply them. Build settings are different: saving them starts a new build immediately.
  </Accordion>

  <Accordion title="Can I deploy only one edited service?">
    The Deploy dialog reviews the saved draft for the whole environment. Check all listed changes before confirming; selecting a service does not limit the deployment to it.
  </Accordion>

  <Accordion title="Does a rollback undo database changes?">
    No. Restoring and deploying a configuration does not restore database records or the contents of volumes. Use your database's backup and migration procedures to recover data.
  </Accordion>

  <Accordion title="Can I deploy to multiple environments together?">
    Deploy each environment separately. Changes to a staging draft do not deploy production. Test the configuration in staging before deploying it to production.
  </Accordion>
</AccordionGroup>
